# План автоматической проверки верстки книг

## Архитектурное решение

Проверку следует встроить в существующий `audit-mod` отдельной клиентской
командой `/liminal_ru_layout_audit`.

Основной и блокирующей проверкой должен быть runtime-аудит внутри Minecraft,
использующий реальные шрифты, масштаб GUI и код отрисовки книг. Статический
анализ ресурсов можно добавить только как быстрый предварительный фильтр:
длина строки без фактической верстки не позволяет надежно определить
переполнение.

## Область проверки

Автоматически проверяются объективные дефекты:

- выход текста за границы страницы;
- пересечение текста с кнопками, прогрессом, закладками и другими
  зарезервированными областями;
- обрезание текста scissor-областью;
- наложение текстовых строк друг на друга;
- заголовки и подписи, не помещающиеся в заданную ширину;
- дефекты, возникающие в `ru_ru`, но отсутствующие в `en_us`.

Субъективные признаки не должны блокировать сборку: неудачный перенос,
слишком короткая последняя строка или визуальный баланс страницы. При
необходимости они выводятся как `WARN`.

## Этапы разработки

### 1. Подготовить минимальный контрольный пример

Сохранить старый проблемный текст `botania.landing` как тестовую fixture и
добавить один корректный вариант той же страницы. Этого достаточно для
первичной проверки всей цепочки: обнаружение пересечения, формирование отчета
и отсутствие ложного срабатывания после исправления.

### 2. Добавить индекс экранов книг

Расширить генерируемый `translation-audit-index.json`: хранить движок книги,
ID книги, ресурс, entry/page и источник текста.

Индекс должен охватывать реальные страницы загруженной книги, а не только
записи манифеста перевода. Это необходимо для проверки нативных русских строк,
которые не проходили через каталог переводов, как прежний
`botania.landing`.

### 3. Реализовать общее ядро аудита

Добавить в `audit-mod` пакет `layout` со следующими основными компонентами:

- `LayoutAuditRunner` управляет проходом;
- `LayoutAdapter` описывает интеграцию с конкретным движком книг;
- `LayoutCapture` собирает геометрию отрисовки;
- `LayoutRegion` представляет текстовые и зарезервированные области;
- `LayoutIssue` описывает найденный дефект;
- `LayoutReportWriter` сохраняет результат.

Ядро должно собирать экранные bounding box текста после применения
трансформаций, границы страницы, scissor-области и прямоугольники элементов
управления.

### 4. Реализовать Patchouli MVP

Первый адаптер должен покрыть:

- landing screen;
- категории и списки записей;
- обычные текстовые страницы и заголовки;
- нижние кнопки, прогресс и закладки.

Адаптер программно открывает каждое состояние книги, ждет стабилизации
нескольких кадров и запускает анализ. Заблокированные progression-записи
нужно открывать напрямую для аудита, не изменяя игровой прогресс.

Критерий готовности MVP: старая строка `botania.landing` дает
`TEXT_INTERSECTS_CONTROL`, а сокращенная строка проходит проверку.

### 5. Добавить отчет и снимки проблем

Результат сохранять в:

`liminal-industries-ru-audit/book-layout-audit.json`

Для каждой проблемы записывать:

- книгу и страницу;
- JSON pointer или translation key;
- правило и серьезность;
- координаты текста и препятствия;
- разрешение и масштаб GUI;
- путь к снимку экрана.

Снимки создавать только для проблемных экранов. Для просмотра результатов
можно дополнительно генерировать простой HTML-индекс со ссылками на снимки.

### 6. Добавить сравнение языков

Выполнять проходы для `en_us` и `ru_ru`. Если дефект присутствует в обоих
языках, классифицировать его как `UPSTREAM_LAYOUT`. Если проблема возникает
только в русском переводе, классифицировать ее как `TRANSLATION_LAYOUT`.

Так исходные дефекты модов не будут смешиваться с регрессиями перевода.

### 7. Подключить остальные движки книг

После Patchouli реализовать отдельные адаптеры:

- Mantle/Tinkers' Construct;
- руководство Immersive Engineering.

Общее ядро остается единым, но перечисление страниц и зарезервированные
области у каждого движка свои. Универсальный парсер разметки для всех движков
не требуется.

### 8. Автоматизировать запуск

Добавить Gradle-задачу `runLayoutAuditClient`, которая:

- запускает тестовый клиент с `ru_ru`;
- входит в подготовленный локальный мир;
- выполняет аудит;
- сохраняет отчет;
- завершает клиент с ненулевым кодом при наличии `ERROR`.

Сначала задачу следует использовать локально перед выпуском перевода. После
стабилизации ее можно запускать по расписанию в CI под Xvfb. Для обычных
изменений ресурсов достаточно быстрого статического preflight, который не
блокирует сборку.

## Минимальная стратегия тестирования

Чтобы не создавать дорогую и хрупкую тестовую инфраструктуру, достаточно:

1. Одного параметризованного unit-теста для пересечения прямоугольников,
   выхода за границы и clipping.
2. Одной fixture-проверки: старый `botania.landing` должен падать, исправленный
   вариант должен проходить.
3. Одного клиентского smoke-теста команды `/liminal_ru_layout_audit`, который
   подтверждает создание корректного JSON-отчета.

Для Mantle и Immersive Engineering отдельные исчерпывающие наборы тестов не
нужны. Их первый полный runtime-проход проверяется по отчету и нескольким
снимкам вручную. Новые автоматические regression-тесты добавляются только
после обнаружения реального дефекта, который текущие проверки пропустили.

## Порядок внедрения

Первая итерация: общее ядро, Patchouli landing/text pages, JSON-отчет и снимки
ошибок. Она закрывает класс дефекта с наложением текста на кнопки.

Вторая итерация: сравнение `en_us` и `ru_ru`, затем адаптеры Mantle и
Immersive Engineering.

Третья итерация: автоматический клиентский запуск и подключение к CI после
того, как уровень ложных срабатываний станет приемлемым.
